# Research Workbench 资源监控页面设计

## 目标

为 Research Workbench 增加独立的“系统监控”页面，实时展示 **Research Workbench 自身及其子进程** 的资源占用，回答“当前占用多少”和“哪个 Research Workbench 进程在占用”。

监控范围仅包括承载当前 API 的进程树：API 进程本身及其递归子进程。它不会枚举、存储或展示操作系统中其他应用的进程信息。现有“运行监控”页面继续负责数据源事件流、队列和 Worker 运行状态；新页面聚焦资源使用。

## 已确认的决策

- 第一阶段采用“进程树 + 任务归因”方案：以进程为可靠的归因单位，并为已知 Research Workbench Worker 显示职责标签。
- 不新增 Python 依赖。项目已声明 `psutil>=5.9.0`，用于跨平台采集 CPU、内存、线程数、磁盘 I/O 和网络 I/O。
- 采样周期为 2 秒；浏览器只保留最近 5 分钟（150 个点）的序列，不持久化高频资源样本。
- 页面展示主进程及递归子进程；进程按当前 CPU 使用率降序排列。
- 初期不采集单个函数、HTTP 请求或外部程序的资源使用，也不改变爬虫/管线的启动协议。未知进程显示安全的命令摘要和 PID，而非猜测业务任务。

## 页面与交互

在主导航中增加“系统监控”入口，打开独立内容区。

1. **实时状态栏**：Research Workbench 总 CPU、总内存（MiB）、进程数、磁盘读/写速率、网络连接数、最后采样时间和采样健康状态。
2. **趋势区**：并列的 CPU 与内存折线图。两图共用时间范围（最近 5 分钟），悬停显示该时间点的数值；每 2 秒向右追加一个点。
3. **进程占用表**：列为进程/职责、PID、CPU、内存、线程、磁盘 I/O、网络连接、状态。数值右对齐且使用等宽字体；表头支持 CPU、内存和 I/O 排序。
4. **进程详情抽屉**：选择一行后，在右侧展示命令摘要、父 PID、启动时间、当前状态和最近一分钟 CPU/内存小趋势。进程在详情打开期间退出时，保留最后样本并明确标记“已退出”。
5. **空/异常状态**：API 进程身份不可用时不显示整机数据，改为“未发现 Research Workbench 进程”；采样暂时失败时保留最后成功帧，显示失败时间和可重试提示。

页面沿用 `app/web` 原生 HTML、CSS、JavaScript 架构和既有高密度运营界面规则；不引入 React、Vite、Tailwind 或图表库迁移。

## 后端设计

新增一个专用资源监控服务，职责单一：根据当前 API 进程 PID 构造受限进程树，采集并归一化资源快照。

### 进程边界

根进程默认使用 `os.getpid()`。采集器通过 `psutil.Process(root_pid).children(recursive=True)` 收集后代，并始终将根进程包含在结果中。每次采样重新发现树，避免遗漏后来启动的 Worker，并自动移除已经退出的进程。

每个进程记录：`pid`、`parent_pid`、`name`、安全命令摘要、`create_time`、`status`、CPU 百分比、RSS 内存、线程数、累计磁盘 I/O、网络连接数/可用性和职责标签。累计磁盘 I/O 在服务内与上次采样做差，转为每秒速率；无权限或平台不支持的字段返回 `null` 与稳定的 `unavailable_reason`，而不是伪造 0。第一期不显示按进程网络字节数：`psutil` 没有跨平台可靠的按进程网络收发字节接口，系统级网络计数不能安全归因给 Research Workbench。

CPU 是两次非阻塞采样间的进程 CPU 百分比。服务首次建立基线时返回 `warming_up=true`，前端仍能显示内存和进程列表，但 CPU 与速率显示“采样中”。

### 职责标签

仅使用现有可验证信息：根进程标记为 `API`；由 Worker 状态注册信息命中的 PID 标记为 `知识加工 Worker` 或 `调度器`；其余进程标记为 `Research Workbench 子进程`。标签不是授权边界，也不依赖命令字符串猜测。后续若任务启动上下文增加稳定标签，可在不改变 API 主结构的情况下扩充映射。

### API 契约

新增只读端点：

- `GET /api/system/resource-usage`：返回单次总览和进程列表。
- `GET /api/system/resource-usage/history?window_seconds=300`：返回内存环形历史中的总 CPU/总内存时间序列，窗口最大 300 秒。

每项响应均含 `sampled_at`、`root_pid`、`status`（`ok`、`warming_up`、`degraded`、`unavailable`）及结构化告警。不会将 `psutil.AccessDenied`、`NoSuchProcess`、平台差异的异常直接暴露给浏览器。

路由保持轻薄，只负责依赖注入、输入验证和 HTTP 映射；采样、进程过滤、速率计算和标签映射都在服务中完成。所有异常路径使用项目 `get_logger` 记录结构化日志，包括根 PID、受影响 PID、错误类别和降级字段，且不记录完整命令行中的潜在秘密值。

## 前端数据流

页面激活后，前端立即请求快照与历史，再以 2 秒间隔请求快照。最新快照驱动状态栏和进程表；成功快照追加到有上限的本地序列，图表只更新增量。页面离开、浏览器标签不可见或网络请求被替换时停止轮询并取消在途请求，避免后台采样造成不必要负载。

不使用 SSE 作为第一期通道：2 秒 HTTP 轮询能够与现有监控模块一致地处理取消、超时和错误恢复，且采样量很小。后续需要秒级以下刷新或统一运行事件总线时，可在不改响应模型的前提下添加 SSE。

```text
浏览器“系统监控”页面
  └── 每 2 秒 GET /api/system/resource-usage
        └── ResourceMonitoringService
              └── 仅 os.getpid() 及递归子进程（psutil）
                    ├── 当前资源快照
                    └── 内存中的 5 分钟聚合历史
```

## 错误处理与性能

- 一个子进程在枚举后退出：跳过该进程并将该次样本标为部分可用。
- 根进程不存在或无法访问：返回 `unavailable`，HTTP 保持 200，以便前端展示受控空状态；仅发生配置/调用错误时返回 4xx/5xx。
- 单个字段不可用：字段为 `null`，并携带原因；不影响其余进程或指标。
- 所有采样均限制在进程树内，且不写数据库；服务维护固定长度的内存环形缓冲，防止长期运行时内存增长。
- 前端连续失败时采用有限退避（最多 10 秒），恢复成功后回到 2 秒周期，避免 API 不可用时产生请求风暴。

## 测试与验收

### 后端

- 使用模拟 `psutil` 进程树验证只采集根 PID 与后代，不包含同机无关 PID。
- 验证总 CPU/内存聚合、速率差分、CPU 预热、固定长度历史和排序字段。
- 验证 `NoSuchProcess`、`AccessDenied`、I/O 不可用、根进程不可用等降级响应与日志调用。
- 验证 API 响应模型、窗口参数边界和不会泄露完整命令行。

### 前端

- 静态测试覆盖导航入口、轮询启动/停止、请求取消、历史上限、数值格式化和异常状态渲染。
- 用真实浏览器检查：初始预热、正常实时刷新、进程表排序、详情抽屉、页面离开后停止轮询，以及 API 暂时失败时保留上一帧。

实现时更新 `docs/modules/app_api.md`、`docs/modules/app_web.md`、`docs/FILE_GUIDE.md` 和 `docs/CHANGELOG.md`，并按项目规则在 `.ai/reports` 留存任务报告。由于本功能不涉及桌面壳、sidecar、安装包或路径配置，不触发桌面跨平台打包验收；`psutil` 的跨平台字段差异仍由 API 降级契约与测试覆盖。

## 非目标

- 不监控整台机器或其他应用。
- 不新增告警阈值、通知渠道、远程采集或长期指标存储。
- 不实现以函数、请求或未经显式运行上下文标记的业务任务为单位的精确资源归因。
