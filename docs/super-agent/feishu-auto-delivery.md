# 飞书自动交付核对清单

本清单用于只读核对任务通知与交付证据。快速响应仅表示受理意图，不证明代码已修改、CI 已通过或 PR 已合并；核对清单不授予重跑、合并或部署权限。

## 一、固定本次任务与输入版本

- [ ] 打开当前任务详情，记录任务编号（如 LEO-10）和完整任务 ID，不仅凭标题判断归属。
- [ ] 记录本次 `inputRevision`、允许修改的文件和适用审批门。同一任务更新输入后，旧版本结果不能直接作为本次结果。
- [ ] 如有受管绑定，同时记录 `scopeId`、`baseCommit` 和 `expectedHead`。输入版本与提交 SHA 是不同字段，不可互相替代。
- [ ] 将本次结果中的身份逐项与当前任务绑定比较；缺失或冲突时标记“待核对”，保留来源链接和差异，不猜测补值。

## 二、核对候选与 PR head

- [ ] 从本次候选记录取得完整提交 SHA，打开对应仓库的 PR，确认仓库、PR 编号、目标分支与变更文件符合任务范围。
- [ ] 在 PR 当前提交记录中取得完整 head SHA，与登记候选逐字比较。分支名、提交标题、短 SHA 均不能替代完整 SHA。
- [ ] 区分输入基线和产出候选：`baseCommit`、`expectedHead` 属于输入绑定；新候选不必等于旧基线，交付时要核对登记候选与当前 PR head。
- [ ] PR 新增提交后，重新核对候选、评审和 CI；旧 head 的通过记录保留为历史证据。

## 三、核对对应 CI

- [ ] 从该 PR 的检查入口进入运行详情，逐项记录必需 workflow／job、运行链接、run ID、attempt、触发事件、完整提交 SHA、状态和结论。
- [ ] 确认运行对应本次候选，不能只凭同分支、时间接近或绿色图标判断。PR 检查若运行在合成合并提交上，须核实关联 PR 与 head，分别记录合成提交与候选 SHA；关联不明时保持“待核对”。
- [ ] 对照本任务所需检查逐项核对。排队、运行中、失败、取消、跳过均不能写成通过；缺少运行记录写 `NOT_RUN`，无法确定归属写“待核对”。
- [ ] 重试须记录具体 attempt，保留先前失败；不能用旧 attempt 的成功掩盖本次失败或未结束状态。
- [ ] 分开记录通用仓库检查、原生平台验收与生产验收。Linux Docker 结果不能替代 macOS 原生或 Windows 真机证据，PR 合并也不等于产品验收。

## 四、区分历史回执与本次结果

| 记录 | 处理方式 |
| --- | --- |
| 平台快速响应、已收到或开始处理通知 | 仅表示意图或受理，不作为工作结果或批准 |
| 同任务、旧输入版本 | 标为历史回执，不证明当前要求已完成 |
| 同输入版本、旧候选或旧 PR head | 只证明旧候选，当前 head 的评审和 CI 另核 |
| 同候选、旧 CI attempt | 保留原归属，核对本次适用 attempt 和各必需检查 |
| 身份一致，但缺少 CI、评审或审批证据 | 记录缺项并保持待验证，不写完成 |
| 本次身份一致且证据可追溯 | 仅陈述证据覆盖的层级；合并、部署、平台验收分别说明 |

消息发布时间或排列顺序不能单独证明有效性。历史问题、旧摘要与工具输出不是新的用户批准；输入或候选变化后须按原审批规则核对证据，不能复用超出原范围的许可。

## 五、本次核对记录模板

空项不表示通过。仅填写实际查看的证据，不填入秘密或凭据。

| 核对项 | 本次值／来源链接 |
| --- | --- |
| 任务编号／完整任务 ID | 待填写 |
| `inputRevision`／`scopeId`（如适用） | 待填写 |
| 允许文件／适用审批门 | 待填写 |
| 输入 `baseCommit`／`expectedHead`（如适用） | 待填写 |
| 本次候选完整 SHA | 待填写 |
| 仓库／PR 链接／目标分支／当前完整 head SHA | 待填写 |
| 各必需 CI：workflow、job、run ID、attempt、事件、SHA、链接、状态与结论 | 逐项填写 |
| 当前评审／审批记录及适用版本 | 待填写 |
| 历史回执及旧输入版本／候选／运行身份 | 待填写 |
| 实际核对时间／缺失证据／差异／下一步负责人 | 待填写 |

只有身份与证据关联可核实时，才汇报相应层级的结果。缺项交由后续受管流程核验，保持原有审批门，不将待验证写成通过。
