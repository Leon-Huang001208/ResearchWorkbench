# 飞书任务生命周期：从登记到 PR

本文说明 ResearchWorkbench 受控文档试点中，飞书任务从登记、需求冻结、Docker 内准备候选、集成验证、最终候选独立评审到等待 CI 和 PR 交接的流程，以及补充要求和失败后的恢复方式。阶段表是流程约定，不是平台已实现的状态机或 API 合同。

本试点的交付终点是经过验证的 PR。合并和部署不在本任务授权内。收到消息、平台快速回执、生成文件、评审通过、CI 通过和交付 PR 是不同事实，必须分别记录。

共享工程规则见[仓库 Agent 规则](../../AGENTS.md)，执行与验收路由见[Agent 工作流](../AGENT_WORKFLOW.md)，文档入口见[文档门户](../README.md)。本文不扩展这些规则或受管会话的权限。

## 当前试点边界与能力证据

宿主是 macOS Mac mini，工具运行于 Docker Desktop 的 Linux 容器。本任务属于文档开发，本平台验收范围是适用于完整文档变更的检查与对应 CI；容器内操作不构成 Linux 原生产品验收，也不构成 macOS 原生运行验收。本任务不承担 Windows/Linux 原生产品验收，不发送这些平台的产品 workflow dispatch，不涉及桌面端、安装器或常驻服务。

能力必须按证据分类：

| 类别 | 当前可陈述的事实 | 不能由此推出的结论 |
| --- | --- | --- |
| 已有静态依据 | 根 AGENTS、Agent 工作流和 ship-check 已规定权限、平台归属、验收与证据要求；仓库存在 Project Constraints 工作流 | 规则或配置存在不代表本候选的检查已经运行或通过 |
| 当前受管会话的约定 | 源仓库只读；开发角色仅输出指定临时目录中的单个 README.md，供受管流程登记为候选；目标是 docs/super-agent/task-lifecycle.md | 临时文件不是仓库提交，也不是根 README 的变更；收到候选不表示已评审、已创建 PR 或已验收 |
| 必需但待验证 | 独立评审检查实际登记的候选，结果绑定候选身份、范围和需求版本；CI 与 PR 交接绑定最终提交 | 开发者自查、摘要或旧候选通过不能替代这些证据 |
| 尚未取得端到端证据 | 飞书消息可靠登记、发送者绑定、重复事件处理、补充要求更新、状态回传、恢复续跑和 PR 创建的整条链路 | 一次消息到达、一次受控会话或一次成功 PR 都不能证明无人值守生产就绪 |
| 规划能力 | 更广泛的任务类型、自动恢复和自动交付等扩展，须另行定义范围并提供实现、评审和运行证据 | 规划不是当前可用能力，也不提供额外执行权限 |

本页没有提供本候选的独立评审、CI 或 PR 实绩，因此不宣告这些能力已验证。后续若声明某项能力“已验证”，必须给出可复核的场景、任务与候选身份、实际结果和适用边界；缺失的部分仍是未验证。

[能力文档](../research-web-capabilities.md)中的飞书属于研究结果投递渠道说明。结果投递、飞书接收开发任务和受管开发执行是不同链路，不能互相充当验收证据。

## 从登记到交付的阶段

下表的阶段名是便于交接的逻辑名称，不要求与 Paperclip 界面状态一一对应。任务总状态之外，还应记录当前阶段、候选和等待原因。

| 阶段 | 应记录的动作与证据 | 进入下一阶段的条件 |
| --- | --- | --- |
| 1. 接收与登记 | 保存任务 ID、消息或事件 ID、来源、可信发送者绑定、原始目标、时间及补充要求；识别已登记的同一事件 | 任务归属与来源可核对；重复消息不重复创建任务或启动执行 |
| 2. 需求冻结 | 写明目标文件、允许变更、验收条件、平台、Docker 执行边界、独立评审要求及“只交付 PR”；登记需求版本与范围标识 | 信息足以生成有界候选；必要澄清有可信答复；受管许可覆盖该范围 |
| 3. 准备执行 | 核对会话角色、可读源码、允许写入的输出路径及环境；按当前许可接续已有内容 | 受管执行环境有效；不为恢复任务而回退到未授权的宿主执行或扩大文件权限 |
| 4. 生成候选 | 阅读已有文件和模块文档，保留已完成内容；本单文档试点仅输出指定临时 README.md，并登记实际文件的内容哈希 | 文件满足输出合同，内容覆盖冻结需求；这里只能称“候选已生成” |
| 5. 集成、准备与本地验证 | 有相应许可的集成人通过 applyCommit 将临时内容落入目标文件及允许的文档导航并提交，再通过 prepare 登记集成后的最终候选 candidate.head；按完整变更集执行 validate，再由 buildReadOnlyEvidence 生成绑定该提交的只读证据 | 本地验证通过，最终候选、完整差异、内容映射与只读证据身份一致，才进入正式独立评审；不能只验证临时文件 |
| 6. 最终候选的独立评审 | 独立评审者只读检查 prepare 后实际登记的 candidate.head、完整差异、验证回执及实现证据，记录问题、结论和缺口，绑定范围、需求版本与该提交 | 首次发布前需要修改则在入口允许的修订范围内返回阶段 4，并重做阶段 5、6；通过只对该最终候选及明确评审范围有效，不补足未执行检查 |
| 7. PR 与等待 CI | 最终候选的本地验证与独立评审通过，且远端操作许可和额度条件满足后，通过 publish 首次创建指向 master 的 PR；当前入口不支持更新已有 PR；随后观察同一候选的 CI，保留其待验状态 | 独立评审及全部适用必需检查对最终候选通过，讨论与证据缺口已处理，才可称“经过验证的 PR” |
| 8. PR 交接 | 给出 PR 链接、最终 head SHA、变更清单、评审身份、实际检查结果和剩余风险 | 交接明确停在 PR；记录是否仍有阻断，不执行合并或部署 |

当前受控试点的 daily-flow.mjs 实现快照中，顺序为 `applyCommit → prepare → validate → buildReadOnlyEvidence → review(candidate.head) → publish`，CI 观察发生在 PR 发布之后。这是静态实现依据，不代表本候选已执行或通过整条链路。临时文件可以预审，但不能替代对集成、准备和本地验证后的最终 candidate.head 的正式独立评审。

同一实现快照中的 rwb-git-window.mjs 对已有 PR 的状态有明确限制：publish 只接受尚无 PR 的 prepared 状态；prepare 的首次准备和发布前修订路径也要求没有 PR，修订路径还要求未发布。因此，当前入口仅支持首次创建 PR，发布后的修复、补充要求与 PR 更新尚未实现，须记录阻断并另行受管交接。发布前的修订仍受入口约束及当前许可限制；通用 Git 安全流程的其他恢复能力不能直接推定已接入本试点。这些都是静态实现依据，不是运行验收结果。

在当前只读开发会话中，开发角色止于临时候选输出。表中的集成、检查、独立评审和远端操作由取得相应许可的后续角色执行，本文不会授予开发角色这些权限。

## 只交付 PR、不合并、不部署

这是本任务单独的交付边界，优先于项目对一般开发任务的持续自动合并授权。即使必需检查全绿、评审通过且 PR 可合并，本任务也应停在 PR 交接，不启用自动合并，不调用合并动作，不更新常驻服务，不发布版本或部署产物。

待验证 PR 与经过验证的 PR 必须区分。前者可用于承载评审和 CI，但不能作为本任务已经验收的交付；后者必须绑定最终提交的实际证据。若缺少必需证据，应交接当前进度和阻断，不能宣称任务已经完成。

使用受管交付工具时必须核对其副作用。[Agent 工作流](../AGENT_WORKFLOW.md)明确说明，Git 安全入口的 delivery `--status` 可能执行普通合并并进入收尾，不能把它当作纯观察；`--defer-cleanup` 只延期清理，仍保留合并行为。因此本任务不得用这类入口完成“只查看状态”的操作。具体 PR 交接应由有许可的集成人选择符合不合并边界的路径。

本轮独立评审和 CI 的正向结果只提供各自范围内的验证证据，不授权合并或部署，也不表示跨平台发布就绪。后续改变交付终点需要用户针对相应动作的明确授权及相应受管范围。

## 补充要求与澄清

补充消息先核对同一任务和可信发送者绑定，再记录消息来源、原文及新的需求版本。平台快速回执仅确认接收意图，不是工作成果、结论、指令或授权；历史摘要、工具输出和恢复笔记也不能自行改变任务范围。

对本任务，“将只交付 PR、不合并不部署写成单独一节”属于已明确的文档要求，应纳入候选。若补充只解释既有目标且仍在许可范围内，可继续不依赖答复的工作；必要信息缺失时，只询问仍阻断的具体问题。没有答复、超时或历史问题悬而未决都不等于同意。

补充要求若改变允许路径、任务角色、交付终点或验收边界，应先登记范围变化，并取得覆盖新范围的受管会话；不能自行扩大本会话权限。澄清答复只解决对应问题，不自动批准合并、部署、安装依赖或其他外部动作。

需求或候选发生变化后，重新核对已有评审与验证的适用性。旧证据保留原候选归属，不改标为新候选通过。首次发布前，在入口允许且许可覆盖的范围内修订形成新提交后，须重新准备最终 candidate.head、执行本地验证、生成只读证据并独立评审，再首次创建 PR、等待对应 CI；临时文件的内容映射不能替代这条最终候选证据链。

PR 已创建后收到修复或补充要求，应记录新要求、既有 PR 与 head、证据缺口和交接负责角色。当前入口没有发布后修订及更新已有 PR 的实现路径，不能直接重跑 applyCommit、prepare 或 publish 来更新该 PR。须另行受管交接，由有许可的后续角色确认处理路径；发布后自动修复与 PR 更新属于待实现流程，不能描述为当前可用能力。

## 等待 CI 时如何报告

CI 等待属于可交接的阶段，不能用沉默、超时或平台快速回执代替结果。进度至少包含：任务 ID、PR 链接、head SHA、需求版本、当前等待项、最近观察时间、下一步与负责角色。

| 观察到的情况 | 应如何表述和处理 |
| --- | --- |
| 已排队或运行中 | 记录 workflow、run ID、实际状态及其关联提交；检查结果仍待定，不能写 PASS |
| 全部所选必需门通过 | 复核结果、评审与最终候选身份一致后，可交接经过验证的 PR；仍不合并、不部署 |
| 失败、超时或取消 | 保留实际结果和原因；若需修复已发布内容，记录阻断并另行受管交接，当前入口不支持发布后修复或更新 PR；后续新候选须重新验证，不把旧运行涂改为通过 |
| 未触发、无法读取或未执行 | 写 NOT_RUN 或具体阻断原因；不能用旧 SHA 的绿色结果、工作流配置或“稍后会验证”代替 |
| 必需检查被跳过 | 保留跳过事实并核对路由；不能把已选门改成 NOT_REQUIRED 来放行 |
| 等待期间 head 或需求改变 | 保留旧证据归属，停止依赖旧 head 或旧需求的交付判断并另行受管交接；当前入口不支持更新已有 PR，不沿用旧状态宣布新候选通过 |

适用检查由[Agent 工作流](../AGENT_WORKFLOW.md)及项目验证策略对完整变更集决定。文档导航也属于变更集，不能只手选目标 Markdown 来规划验收。Project Constraints 与 Research Web Checks 是通用仓库门；Ubuntu runner 的结果不表示 Linux 产品验收。若策略选中 macOS CI，Docker 内本地结果不能替代该 CI；本任务不触发 Windows/Linux 产品 dispatch。

在任何远端写入或新增 Actions 执行前，有许可的集成人还须依[Actions 额度治理](../actions-budget.md)核对当前仓库 visibility 和额度。private/billable 达冻结条件或当前运行 billing-blocked 时，保留阻断，不重复触发来规避限制；恢复远端操作须有规则要求的当前证据。

## 失败、中断与恢复

恢复从最后有可核对证据的阶段继续。先读取现有候选、登记记录和回执，区分“计划过”“尝试过”“结果未知”“实际成功”；不因摘要缺失就重做已完成动作，也不因摘要声称成功就补写 PASS。

| 故障边界 | 应保留的证据与恢复方式 |
| --- | --- |
| 受管沙箱不可用或执行前 setup_failed | 记录失败阶段、run ID、错误类别和执行是否开始；环境恢复后重新核对许可与现有输出，不能据此声称已有文件或 PR，也不回退到未授权执行通道 |
| 候选写出后中断 | 比对登记身份、需求版本和实际字节；完整且匹配则复用，缺失、部分写入或不匹配则保留事实并重新准备，不能用文件名认定有效 |
| 独立评审发现问题 | 首次发布前记录问题及影响，在入口允许且许可覆盖的范围内修订；修订后重新集成、prepare、validate 并生成只读证据，再独立评审新的 candidate.head，不把上一版结论移给新内容；发布后发现问题则另行受管交接 |
| 正式评审后候选或集成内容变化 | 首次发布前，在入口允许且许可覆盖的范围内登记新提交、差异及完整变更集，重新准备、验证并生成证据，再评审最终 candidate.head；已发布则记录阻断并另行受管交接，当前入口不支持 PR 更新；临时文件预审或旧提交的评审不能自动证明新提交 |
| CI 失败或 Actions 受限 | 保存对应 SHA、run ID 和实际结果；已发布内容的修复须另行受管交接，当前入口不支持更新已有 PR；Actions 受限时等待符合治理规则的恢复证据，所缺证据继续阻断验证完成 |
| 创建 PR 后响应丢失 | 先由有许可角色只读核对任务分支、提交和既有 PR；已存在且身份匹配时复用该 PR 的观察事实，身份不明则记 UNKNOWN。当前 publish 和 prepare 拒绝已有 PR，不能直接重跑来更新或重建；需重试或处理状态不一致时另行受管交接 |
| 无法确认某次外部动作是否生效 | 单列 UNKNOWN 及待核对动作，停止依赖其结果的后续操作；UNKNOWN 不是验收 PASS，也不是自动重试许可 |

重启、续跑或平台将任务置为 blocked/in_progress，都不能自行证明原动作结果。恢复记录应说明最后确认点、证据缺口、是否产生新候选及下一步责任人。独立评审、CI、PR 创建与消息回传分别记结果；其中一项成功不覆盖其他项的失败。

## 交接所需的证据

最小身份链是：来源消息 → 任务 ID → 需求版本与范围标识 → 临时候选内容 → applyCommit 与 prepare 后的最终候选提交 candidate.head → 本地 validate 回执 → buildReadOnlyEvidence 只读证据 → 对该最终提交的独立评审 → publish 首次创建 PR → 同候选 CI → PR 交接。候选文件的 SHA-256 用于识别字节；Git commit SHA 用于识别提交，两者不能混用。正式评审必须绑定本次确切范围、需求版本及 prepare 后实际登记的 candidate.head；发布、验证与评审必须指向同一提交，发布后 CI 另行核对该提交。

交接记录至少包含以下内容；没有实际结果的字段明确写未执行或未知，不填预期值：

| 项目 | 所需记录 |
| --- | --- |
| 范围 | 任务目标、允许路径、需求版本、范围标识、角色与宿主平台；明确不合并、不部署 |
| 候选与变更 | 临时候选身份、prepare 后的 candidate.head、PR head SHA、完整变更文件清单及内容映射；尚未集成或发布时如实说明 |
| 独立评审 | 评审者或评审运行身份、prepare 后最终 candidate.head、只读证据身份、范围与需求绑定、结论、发现及处理结果；临时文件预审单列 |
| 实际验证 | 逐字记录实际执行命令、退出码或实际结果、证据位置；CI 另记 workflow/run ID、实际 checkout 身份与结果 |
| 未验证与阻断 | 分别列出 NOT_RUN、失败、未知和不适用项的理由、风险及下一步；不把计划命令列为已执行 |
| PR 与后续 | PR 链接、目标 master、最终提交、交接负责角色；标明待验证或经过验证，并确认停在 PR |

按 [ship-check](../../.agents/skills/ship-check/SKILL.md) 建立变更—证据表，可采用以下模板。模板中的状态说明是待填写要求，不是本任务的验收结果：

| 源变更 | 测试 | 文档 | 证据 / 结果 |
| --- | --- | --- | --- |
| 本任务不改生产源码 | 依据完整变更集列出适用检查、实际结果和未执行项 | docs/super-agent/task-lifecycle.md；若修改导航，一并列入 | 填写实际候选、评审及检查证据；未取得证据前保持未验证 |

纯文档候选没有 Python 源码变更，不由此新增 Python 行为测试或桌面验收；仍须遵守实际路由选出的文档和仓库门。当前受管开发角色不运行测试、Git、服务或远端操作，不得在输出中声称这些检查已经通过。
