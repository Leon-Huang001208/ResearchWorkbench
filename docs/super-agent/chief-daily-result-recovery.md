# Chief Daily 结果恢复与核对

恢复或复用 Chief Daily 的执行结果前，必须核对任务 ID、输入版本、当前 PR head，以及该 head 对应的 CI 结论，避免将旧任务、旧输入或旧提交的结果当作当前结果。

## 1. 核对任务 ID

从当前任务记录中取得任务 ID，与待恢复结果中的任务 ID 逐字比对。任务标题相同不能替代 ID 一致。若结果缺少任务 ID，或两者不一致，应先查明结果所属任务，不将其用于当前任务。

## 2. 核对输入版本

从当前任务记录中确认输入版本，并与待恢复结果记录的输入版本比对。同时确认对应的需求内容与输入附件属于该版本。若输入版本不同、缺失或无法确认，应将待恢复结果视为待核实，不能直接认定其满足当前需求。

## 3. 核对当前 PR head

打开该任务关联的 PR，确认仓库、PR 编号及目标分支正确，然后记录 PR 当前 head 的完整提交 SHA。将其与待恢复结果记录的提交 SHA 比对，不使用分支名、提交标题或短 SHA 作为唯一依据。

若 PR 在结果生成后新增提交、被强制推送或更新分支，应以更新后的当前 head 为准，重新核对结果与 CI。

## 4. 核对对应的 CI 结论

在 PR 检查页面或 CI 运行详情中，确认运行关联的提交 SHA 与当前 PR head 完全一致，再查看各项必需检查的状态与结论。

- 所有必需检查均已完成并通过，才能记录为“当前 head 的 CI 通过”。
- 任一必需检查失败，应记录为“CI 失败”，并附上失败检查及运行链接。
- 存在排队中或执行中的必需检查，应记录为“CI 尚未完成”。
- 检查缺失、取消、跳过或无法确认是否满足必需检查要求时，应明确记录该状态，不能直接记为通过。

同一检查有重跑时，确认适用于当前 head 的最新运行及其结论。旧 head 的成功记录不能证明当前 head 通过。

## 5. 记录核对结果

恢复结果时保留以下信息，便于复查：

| 核对项 | 记录内容 |
| --- | --- |
| 任务 ID | 当前任务 ID、结果中的任务 ID，以及是否一致 |
| 输入版本 | 当前输入版本、结果中的输入版本，以及是否一致 |
| PR | 仓库、PR 编号及链接 |
| 当前 PR head | 完整提交 SHA |
| 结果对应提交 | 完整提交 SHA，以及是否与当前 head 一致 |
| CI | 对应提交 SHA、必需检查状态、结论及运行链接 |
| 核对时间 | 核对时的时间与时区 |

只有任务 ID、输入版本、结果对应提交均匹配，且当前 PR head 的必需 CI 检查全部通过，才能将恢复结果标记为“已核对，当前 head 的 CI 通过”。任何信息缺失或不一致，都应写明原因及待核实项。PR head 再次变化后，需要重新核对。

## 6. 发布回执丢失时的核对与恢复

发布回执丢失不代表原操作失败。应沿用原任务和原 PR，先核对远端状态，不因缺少回执而重新发布或新建任务、PR。

1. 从原任务的操作记录中取得任务 ID、输入版本、仓库、PR 编号、原操作标识（如请求 ID 或幂等键）、操作时间及预期发布提交的完整 SHA，确认原操作属于该任务和输入版本。
2. 查询原 PR 的远端当前 head，取得完整提交 SHA，与原操作预期发布的 SHA 逐字比对，并查询原操作日志、远端更新记录或发布记录，确认该操作是否已经生效。
3. 若远端 head 与预期 SHA 一致，且记录确认原操作已完成，应恢复并补记回执，关联原操作和原 PR，不再次发布。CI 仍须按前文核对该 head 对应的必需检查，不能将发布成功等同于 CI 通过。
4. 若远端 head 已变化，应查看原提交及 PR 更新记录，确认原操作是否曾生效、之后是否又有更新。不能仅因当前 head 不同就重试，也不能覆盖远端后续提交。
5. 若原操作仍在执行或状态无法确认，应记录为“发布状态待核实”，继续查询原操作及远端记录。只有确认原操作未生效、没有仍在执行的请求，并重新核对远端 head 后，才可在原任务、原 PR 上重试；支持幂等机制时应复用原幂等键。

恢复记录中应保留原操作标识、预期提交 SHA、远端当前 head、操作状态、核对证据及链接、核对时间和是否重试。缺少足够证据时，不将回执缺失视为重试依据，以免重复发布。
