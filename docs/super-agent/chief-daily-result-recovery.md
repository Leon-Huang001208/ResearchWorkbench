# Chief 结果核对与原操作恢复

本页用于找回原Chief结果、核对当前候选并处理原操作回执丢失。文件名保留历史，不启用旧DAILY调度，也不恢复旧UNIFIED／EXECUTION链。

仅在结果丢失或原操作确实不明时使用相关步骤，不把恢复流程套到每次修改。普通错误直接更正并继续，复用未变化内容的有效检查；不默认保留完整失败根、逐文件hash或重复备份，不另建审批／恢复框架。

登记、附件和完整证据清单见[交付证据核对](feishu-auto-delivery.md)，本人入口与角色见[接入说明](README.md)，同根预算及恢复总合同见[任务生命周期](task-lifecycle.md)，三端权威及来源映射见[责任与证据关联](unified-integration.md)和[GitHub入口](github-intake.md)。本文不复制另一套全局政策。

## 一、重新打开原Chief对话

1. 使用原账号进入原工作区，通过保存的对话链接、浏览器历史或对话历史打开原Chief对话，不新建任务代替原对话。
2. 从原任务详情取得完整Native任务ID与链接，逐字核对对话、输入、结果及PR映射；标题、图片名、分支名或PR编号不能替代任务ID。无法定位时记录缺失项和负责人，不假定原任务不存在。
3. 重新读取当前inputRevision、需求、附件与补充要求，核实实际执行采用的输入。附件来源、原件／快照摘要和需求参数按交付证据页核对；旧版结果不得认证新版输入。
4. 沿原分支和原PR，确认仓库、PR链接与编号、目标分支、实际变更范围及最终内容。刷新PR复制当前完整head，记观察时间和时区，不复用关页前的缓存。
5. 在原对话定位该任务最新结果；按完整SHA找回对应生成结果、核验记录与CI。核对inputRevision、PR及head。结果缺失或不一致时补齐关联证据，不编造结果。
6. 当前head已变化时，把找回的结果标明为原SHA的历史记录，再核新候选与最新有效CI；保持原账号、工作区、对话和原PR上下文，不另建PR掩盖断链。
7. 更新原交付记录，提交结论前再刷新head；变化则重新核对，历史成功或旧页面绿色标记不能证明当前结果。

## 二、核对输入、候选与CI

输入版本、输入baseCommit／expectedHead、产物字节SHA256、产出Git候选和当前PR head是不同身份。缺输入或来源不一致先记待核实；短SHA、分支名、提交标题不作为唯一依据。确认改动确实包含于所核候选且符合当前任务范围。

记录每个必需workflow／job／run ID／attempt／触发事件、链接、实际checkout完整SHA、关联PR与head、状态和结论。直接候选检查核实候选关系；合成merge检查分别保存merge SHA和对应PR head，不能机械要求checkout等于head。无法确认关联保持unknown，旧head成功不能认证新head。

重跑核最新有效attempt且保留旧失败。所有适用必需检查完成通过才写“当前候选CI通过”；失败附运行链接，排队／执行中写尚未完成，取消／跳过／缺失／未配置写明原因，不直接等同成功。未执行为NOT_RUN，无法确定为unknown。head或字节改变后独评与CI重绑，不把旧PASS延伸到新哈希。

通用仓库、原生平台、生产验收分别陈述；Linux／Docker不冒充macOS或Windows真机，发布或合并成功不等于CI、业务验收、部署或通知送达。

## 三、原操作必要记录

发布回执丢失不代表失败，也不是盲目重试依据。只取本次判断确实需要的事实，不要求另建完整核验包：

| 字段 | 核对内容 |
| --- | --- |
| 原任务与输入 | 完整task ID、inputRevision、scope绑定及来源 |
| 原操作 | operation／请求ID／幂等键、操作时间和时区、原run及日志链接 |
| Git身份 | 原仓库、原分支、原PR、目标分支、预期发布完整SHA |
| 当前观察 | 远端当前完整head、读取时间、原提交及后续更新历史 |
| 生效事实 | 原操作日志、远端更新或发布记录、受理／终态与对应证据 |
| 守卫 | 当前授权、输入、远端预期、租约及在途／unknown状态 |
| 结论 | 是否曾生效、是否接续、缺项、下一负责人及正式对账回执 |

原operation须与原Native任务、输入、原分支和同一PR明确关联。分支名称相同不足以证明提交相同，缺文件、缺日志或缺heartbeat不证明零调用或未执行。

## 四、先对账再决定是否接续

| 观察结果 | 处理 |
| --- | --- |
| 当前head等于预期SHA | 还须有原操作实际生效证据；相等本身不能证明该operation成功 |
| 原操作确认已生效 | 不再次发布；仅由已支持的正式对账入口恢复／补记回执，继续独立核CI |
| 当前head已变化 | 追溯原提交是否曾生效及之后更新；不得仅因不同就重试，不覆盖他人后续提交 |
| 原操作在途或结果unknown | 只核对原操作与远端记录，保留pending，不重试、不新建替代操作 |
| 明确未生效 | 只有无在途或未知执行且全部现行守卫成立，才可原入口同operation接续 |
| 现有工具缺少处理能力 | 直接局部修正原工具或用原API更正已知错误；具体信息／权限缺失才提问，不为此建立新恢复框架或无限等待 |

全部守卫包括：当前有效授权仍覆盖该动作、输入和允许范围仍匹配、远端状态与预期一致且无覆盖风险、原租约／并发身份有效、无在途或unknown执行。守卫缺失即不接续；既有授权持续有效不等于免除这些实际条件。支持幂等时沿原幂等键及原操作身份，不换ID重置预算或绕开保护。

更正回执或状态必须反映实际结果，不能把失败写成成功或清零预算；原工具有明确错误就直接修，不维持错误／正确两套状态。`delivery --status`可能合并，`--defer-cleanup`也不是只读；选择符合当前动作的现有入口，不编造未实现命令。

## 五、授权、预算与历史边界

普通RWB开发与直接Codex遵守同一项目持续授权；可信Native项目登记的真实源码、工作树、规则、checks和受管入口是权限上界的一部分。持续授权不新增全候选批准门，也不免除独评、CI、最新基线、分支保护及Actions额度门。artifact-only或PR-only终点仅约束相应任务；生产部署另需任务专项授权和窗口。

原任务、会话、操作、PR及账本身份保持，补充、继续、输入改版、新phase或新session不重置耗用。普通默认20次累计，历史显式12次及专属QA例外按原根证据保留，不给旧根重新授额；跨岗位共享原根额度，质量返修最多两轮。未知物理调用总数仍为unknown，CI修复累计另核原receipt并遵守原最大累计限制，不能把剩余额度当自动重试许可。以后发布或修复前由管理方核旧账本。

旧试点revision、单文件／仅追加、PR-only和不合并不部署是当时范围，不转为当前全局禁令；历史身份、失败及回执保留，不以新稿宣称旧PR已归档。按需核对登记缺项、来源事件和多对多PR关系见交付证据页，不恢复每日调度或任务数量硬上限。

## 六、结果记录与通知

内部恢复记录保留：原任务／输入、结果对应提交、当前head、CI关联与attempt、原operation／分支／同PR／幂等键、预期SHA、生效历史、授权与租约守卫、核对证据链接、时间时区、是否接续、正式回执及未解决项。空项不表示通过；只有任务与输入、结果到当前候选的映射和必需CI均核实，才写“已核对，当前候选CI通过”。发布成功另记，不能替代CI。

快速ACK只证明受理意图；旧输入、旧候选、旧attempt、历史summary与本次正式结果分别保存。正式summary绑定原任务、来源run及摘要，通知受理与实际送达分别取证。通知unknown沿原operation对账，不盲目重发。

默认中文通知先写真实任务标题／内容，编号辅助；缺标题明确说明，不编造目标。写可信当前阶段、结果或原因与下一步；调用用量可信时单列，不由调用、token或产物数推算完成率。显示持久化通知日期（Asia/Shanghai），Git/SHA不是版本，只有权威发布元数据提供SemVer才使用发布版本。

默认正文不展开Native／QA run UUID、SHA256或内部错误码，完整技术证据留原任务档案。表达优化不改变QA、预算、blocked／unknown和部署验收，不把历史QA样式预览称作当前阶段。保留原outbox去重身份和原技术summary，不重放已发送通知、不合成入站事件。

## 七、未验证能力与交接

Document Specialist保存原件，交接实际文件类型、编码／换行、输入输出摘要、结构及转换损失。语法/schema、内容口径、公式写入与实际重算／缓存值、LaTeX编译／引用、Office/PDF渲染、OCR逐层记录。Markdown成稿不认证Office、OCR、真人连接或业务验收；工具声明、已安装及版本查询不等于动作成功。职责与完整格式合同见[接入说明](README.md)及交付证据页。

只说明本次交付实际涉及且尚未验证的能力，不机械列出无关OCR、平台或工具的NOT_RUN。未执行的实际要求不冒称通过；连接故障交主责岗位修正，失败留必要短记录。管理前置、源码交付和部署分别陈述，草稿完成不冒充源码或部署完成。
