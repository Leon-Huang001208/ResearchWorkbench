# GitHub 自动化任务入口

本人在 GitHub 创建 Issue，写明目标、允许修改的范围和验收要求，再添加 `agent:ready`，表示提交自动化任务准入申请。标签不代表已受理、已完成，也不扩大任务授权。

## 从 Issue 到结果

1. **准入**：入口核对仓库、Issue 创建者是否为本人、`agent:ready` 标签及任务范围。权限或要求不明确时，记录原因并等待必要信息，不自行扩大范围。
2. **去重**：以仓库和 Issue 身份关联已有任务；重复标签事件或重试应复用关联记录，避免重复创建 Paperclip 任务或并行开发。受理状态不明时先核对，不盲目重试。
3. **Paperclip 任务**：准入后建立或关联任务，保留 GitHub Issue 链接、目标、范围及审批边界。平台快速回执仅确认收到意图，不是执行结果。
4. **开发与独立评审**：开发者在获准范围内生成候选；独立评审检查同一候选的实际差异、需求覆盖和证据。发现问题先修正，再评审；缺失证据明确标为待验证。
5. **PR 与 CI**：由受管交付流程提交 PR，关联原 Issue，列出变更、评审结果、实际检查及未验证项。CI 状态必须对应实际候选提交；未运行、失败或受额度限制时如实记录，不能写成通过。
6. **飞书结果通知**：预期发送任务结果摘要、Issue/PR 链接、CI 状态和阻断项。通知投递与开发结果分别记录；未确认送达不能宣称通知成功，通知失败也不能改写 PR/CI 事实。

## 只交付 PR，不合并、不部署

本任务的交付终点是 PR。即使评审和 CI 通过，也不自动合并到 `master`，不部署、不更新常驻服务、不发布版本。`agent:ready` 及快速回执均不构成这些操作的授权；后续操作须另行明确授权并满足项目门禁。
