# Minimal Bug Fix

以可复现的失败锁定回归，再以最窄改动修复它；“看起来相关”的清理不是修复范围。

## RED：先复现，再编辑

1. 阅读根目录 `AGENTS.md` 以及故障区域的直接规则、测试和最近改动。
2. 在任何实现编辑前，固化最小失败复现：输入、期望、实际结果与运行命令。默认新增或更新离故障最近的自动化回归测试，并先观察它因该缺陷失败，而不是因环境、拼写或不相关问题失败。
3. 从复现沿数据/调用路径查找第一个错误条件、映射、优先级或回退；把它写成可证伪的最窄根因假设。

## GREEN：最窄修复

- 仅修改使默认自动化回归测试，或已记录的受控非自动化复现路径，转为通过的根因位置及必要测试。
- 不重构无关代码、不迁移架构、不顺手格式化邻近模块；若发现另一问题，单独记录，不把它塞进当前补丁。
- 修复后运行目标自动化回归测试及适用的相邻测试；使用例外时重跑同一条已记录路径。保留实际结果。

## 受控非自动化例外

仅在当前范围没有合理自动化基础设施，或故障本质只能通过浏览器、HTTP 或手工路径重现时使用；赶时间、测试不方便或不想维护测试都不是例外。

编辑前必须记录最小可重现步骤或脚本、输入、环境/会话前提、期望与实际结果。修复后必须重跑同一路径并记录结果。交付中说明无法自动化的原因、未覆盖风险和仍应补充的自动化测试。

手工、浏览器或 HTTP 路径的证据只验证该路径；未运行自动化测试时，绝不能说自动化测试通过。

## 交付边界

明确分开报告：

| 类别 | 必须说明 |
| --- | --- |
| 已验证修复 | 失败复现、根因、改动，以及自动化测试或受控非自动化路径的实际结果 |
| 未验证假设 | 未运行的自动化测试或组合、外部依赖、环境限制和仍待确认的产品语义 |

没有编辑前的失败复现；在可用自动化下未观察最近回归测试失败；或使用例外却未重跑同一路径时，不能声称修复完成。

## 防错检查

“先改再补测试”、“既然定位到了就一起整理”或“测试应该能过”都不是证据。撤回到最小复现和最窄根因，避免以大重构掩盖故障。
